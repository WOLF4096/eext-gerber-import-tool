## 项目代码级分析（Gerber 转 PCB 扩展 eext-gerber-import）

对当前项目做了基于源码（而非 README）的完整结构分析，关键结论：

- 真实架构是「壳 + 单文件巨型前端」：
  - `src/index.ts`(758B) 仅做入口，`ImportGerber()` 调
    `eda.sys_IFrame.openIFrame('/iframe/ImportGerber.html', 1280, 800, 'ImportGerber')`。
  - **全部业务逻辑在 `iframe/ImportGerber.html`（315KB / 5958 行，单文件内联 CSS+JS）**。
    README 说的「逆向还原算法」等都在这里，不在 src。
- HTML 内部三段式：
  1. `<head>` 内联 CSS（dark 主题，深色面板 + 强调色，画布 320px 侧栏 + 三 Tab）
  2. 内嵌模板常量：`LCEDA_V3_Head_Source`(~28K/125 行，`{"type":"DOCHEAD"}||{...}` V3 行格式)
     与 `LCEDA_V2_Head_Source`(~9K/163 行，`["DOCTYPE","PCB","1.8"]` V2 行格式)
  3. 主 `<script>`(264K chars)
- 主脚本核心对象/函数：
  - `class GerberParser`：RS-274X 解析，方法 reset/parse/handleExt/handleStd/updateBounds/record。
    支持 `%FS` `%MO` `%ADD` `%AM`(仅 Primitive 4 多边形宏)、`G36/G37` 区域、`G85` 槽孔、
    `LPD/LPC` 极性、钻孔文件(M48/T 刀具)识别、2/3 插补(线段/圆弧)。
  - `PadTool`(83K chars，仅 5 方法)：`toMil` / `calcRadiusRatio` /
    `extractRawData`(提取焊盘/过孔/导线/多边形/填充/钻孔/图片/文字) /
    `consolidate`(智能聚合) / `generatePrimitives`(生成 EDA 图元字符串)。这是「逆向还原」核心。
  - 导出：`exportForEasyEDA_Pro`(主力，V2/V3 双版本)、`exportForOther_Pro`、
    `importPrimitivesAPI`(逐图元 API 写入)、`exportForStandard`(**仅 `alert('待后续更新')`，未实现**)。
  - `configureHeader(source,isV3)`：对模板源码打补丁——启用/禁用内层(15~46)、注入埋盲孔规则。
- 输出格式：
  - V3 文件导出 = JSZip 打包 `{name}.epru` + `project2.json` → 改名 `.epro2`。
  - V2 走 `.epcb`。图元 API 注入用 `eda.pcb_Primitive*`。
  - `eda.*` 实际用到 15 个：pcb_PrimitivePad/Via/Line/Arc/Fill/Polyline/Image/String、
    pcb_MathPolygon.createPolygon、pcb_Layer.setTheNumberOfCopperLayers、
    pcb_Drc.get/saveRuleConfiguration、pcb_ManufactureData.getGerberFile、
    sys_Environment.getEditorCurrentVersion、sys_FileManager.setDocumentSource。
- 图层识别：文件名正则 `Gerber_TopLayer`/`Gerber_BottomLayer`/`Gerber_InnerLayer(\d)`、
  `.GTL/.GBL/.GTO/.GBO/.GTS/.GBS/.GKO|.GM1|.GML|.OUT/.GDD`。
  `mapNameToId`：TOP=1, BOTTOM=2, Inner\d → 14+n（Inner1=15）。
- 其它事实：
  - 完全离线：源码中 **无任何 fetch/XHR/axios**，无 localStorage/sessionStorage；
    head 里 jszip/jspdf 的 CDN 引用是注释掉的，运行时走 `/iframe/js/*`。
  - `DEBUG` 开关在源码中被硬编码为 `false`（true 的那行被注释）。
  - 免责声明弹窗：`handleDisclaimer` + `pendingAction` 机制，**不持久化**（每次打开都弹）。
  - 免责声明含「必须在空白 PCB 文档使用」「严禁用于侵权/逆向」「非生产级」等条款。
- 构建：`npm run build` = esbuild 打包 src→dist/index.js(CJS/IIFE) + `build/packaged.ts`
  按 `.edaignore` 过滤后 zip 成 `build/dist/eext-gerber-import_v{ver}.eext`。
  已产出 v3.3.0/3.3.1/3.3.2 三个包。`.eext` 内容确认**不含 src/，含 iframe/ImportGerber.html 全量**。
- 潜在问题点（供后续改进）：
  - `exportForStandard` 空实现但 UI 仍有入口（走 alert）。
  - 宏解析只支持 Primitive 4，roundrect(21)/其他宏会丢失。
  - `importPrimitivesAPI` 中 `let i` 与外层 for 循环变量同名（易混淆，非致命）。
  - 声明 `import * as extensionConfig` 在 src/index.ts 中未实际使用。
  - jsPDF 体积 364KB 已入库；整体单文件 HTML 维护成本高，无模块化/无构建到 iframe。

### 拆分方法与铁律（下次做同类拆分可直接复用）

- **按字节区间切片，不改一个字符**：只额外在文件头加纯注释 banner。
  拆分脚本 `.workbuddy/tmp/split.py`，校验脚本 `.workbuddy/tmp/verify.py`。
- **保持经典 `<script>`（不能用 type=module）**：多个经典脚本共享同一
  全局词法作用域，所以顶层 `const`/`let`/`class` 跨文件依然可见，
  不需要 import/export，语义与原来单脚本完全一致。
- **脚本顺序不可变**：`01→10`。原脚本无「加载期前向调用」，但
  `03-state.js`（`getElementById('main-canvas')`）与 `10-init.js`
  （`resizeCanvas()`/`drawCanvas()`）在加载时就执行，故脚本仍必须放在
  `</body>` 之前且 09 在 10 之前。
- **不要反缩进**：原脚本顶层缩进 4 空格，其中的模板字面量
  （工程头模板、innerHTML 片段）对空白敏感，反缩进会改变模板**值**。
- **外部 js/css 一律加 UTF-8 BOM**：内容含大量中文（含 JS 字符串），
  服务端若不下发 charset，BOM 可确保解码正确。已实测（不带 charset 下发）通过。
- **HTML 引用沿用绝对路径 `/iframe/...`**（与原文件活动的库引用一致），
  保证 EDA 环境零回归。
- `.edaignore` 新增 `/.workbuddy/`，否则测试脚本与 315KB 原始备份会被打进 .eext。

## 代码级优化分析（全部经实测/源码核实）

当前状态：extension.json 已升 **3.4.0**，v3.4.0 的 .eext 已构建且已含拆分模块；
拆分已提交 `b888aaa 拆分代码`；字节等价性复核仍全部通过。
但 **CHANGELOG.md 仍停在 V3.3.2，缺 3.4.0 条目**；package.json 版本仍是脚手架默认 **1.1.1**。

### 高优先级（涉及数据安全 / 构建污染）

1. **写入画布前不校验文档是否为空**（08-export.js）。
   `getDocumentSource`/`blank`/`primitiveCount` 均为 0 次出现；
   通过 `eda.sys_FileManager.setDocumentSource` 直接替换文档源码。
   现有的 `confirmAction()` 只弹「免责声明」，并不知道当前文档是否空白。
   建议：写前统计当前文档图元数，>0 时弹**专门的强警告**。

2. **`npm run prettier:all` / `npm run fix` / husky pre-commit 会重写 iframe 全部文件**。
   `.prettierignore` 未排除 `/iframe/`，实测 `prettier --write` 后果：
   - `jszip.min.js` 97,630 → 160,466 B；`jspdf.umd.min.js` 364,463 → 549,200 B（**+250KB 包体**）
   - 10 个模块 88,885→62,105 等大幅重排；HTML/CSS 也重排
   - **模板字面量内容本身安全**（已逐一比对：仅 `${i+1}`→`${i + 1}` 这类表达式空格差异，
     LCEDA_V2/V3_Head_Source 内容逐字节不变）
   建议：`.prettierignore` 增加 `/iframe/js/*.min.js`（至少），或整个 `/iframe/`。

3. **`DEBUG` 若被改成 true，`confirmAction` 会直接执行、跳过确认弹窗**（03-state.js），
   调试时容易误覆盖文档。建议 DEBUG 只跳过日志、不跳过确认。

### 性能（板子一大就卡）

4. **`drawCanvas`（09-ui.js L139 起）没有视锥裁剪**：无 viewLeft/viewRight/cull，
   每帧 `for (i < commands.length)` 遍历所有可见图层的**全部**图元。
   平移/缩放时全量重画。建议按包围盒裁剪出屏图元。

5. **每个图元都强制 `stroke()` + `beginPath()`**（为切换极性），
   等于放弃 Canvas 路径批处理。建议记录当前极性，仅在极性**变化**时提交。

6. **`importPrimitivesAPI`（08-export.js）是纯同步循环、0 个 await**，
   几万个图元会**卡死 EDA 界面**（README 也承认会卡顿）。
   建议每 N 条 `await new Promise(r => setTimeout(r, 0))` 让出主线程 + 进度提示。

7. 次要：`renderOrder = loadedFiles.slice().sort()` 每帧新建并排序；
   `getZ` 闭包每帧重建；`appLog` 用 `area.value +=`（O(n²)，但调用量小，影响有限）。

### 未完成 / 名不副实

8. `exportForStandard()` 是空壳，只 `alert('待后续更新')`，但 UI 按钮仍在。
9. 光圈宏只解析 **Primitive 4（多边形）**；RoundRect(21) 等宏会丢形状。
   且解析逻辑**重复 3 处**（04-L79、04-L151、05-parseGerberMacros），

12. `LCEDA_STD_Head_Source` 声明但从未使用（空串）。

### 2. drawCanvas 视锥裁剪 + 极性路径批处理（09-ui.js）

**同时修掉一个严重的渲染 bug**（原先未察觉）：
`drawCanvas` 的「极性处理」块在**每条命令**上无条件 `stroke()+beginPath()`，
把同一图层内连续线段的路径批处理彻底打断 —— 下一段从空路径开始 `lineTo`

载入 `-2809515`、平移后 `-1411821639`（载入与平移两种状态都逐一比对）。

具体改动：
- 极性改为只在真正变化时提交：`curPolarity` 变量，`polarity !== curPolarity` 才 stroke+beginPath
- 新增视锥裁剪：按 `viewState` 算出世界坐标可视矩形 `viewRect`，

- 关键：被裁掉的段之后，下一段必须先 `moveTo(segX0,segY0)` 重新起笔
  （`pathBroken` 标志），否则 Canvas 会连出一条横跨屏幕的假直线
- 裁剪覆盖 type 1/3/4；type 2（Move）不裁；type 6（槽孔）保持原样以降低风险

### 3. 写入画布前的空文档校验（08-export.js）

## 新增「处理模式」框架（第一批：框架 + RS-274X + 嘉立创内部标准）

### 背景与需求确认（本次向用户澄清的结论）

「处理模式」下拉要加入 4 个行业标准 + 保留嘉立创内部标准，**根据选择路由到不同模块处理**；

`INDUSTRY_LAYER_RULES` 第一版把「已是字符类的 `_SEP`」又套了一层 `[...]`，

教训：拼接正则片段时，必须清楚该片段是字符类还是分组，不要盲目再加括号。

- 最小复现：正常 Gerber 里加一行 `D4*` 即崩溃（`D11*` 正常）

### 挖出的 5 个根因（更重要）

1. **`extractRawData` 只认嘉立创专业版私有段标记**（`G04 Pad Start/Via Start/Track Start/…`）。
   其它来源（KiCad / Altium / P-CAD / 嘉立创标准版 v6）没有标记 → 焊盘/导线/折线**全部为 0**，
   只剩钻孔能出过孔。这正是"只有钻孔导入成功"。已改为无标记时按「图层+指令类型」推断，
   有标记时行为不变（`hasSectionMarkers` 开关）。
2. **坐标双重单位换算**：解析阶段坐标已换算成 mm，`extractRawData` 又对坐标调 `toMM()`
   （文件单位→mm）。mm 文件看不出，**英寸文件**焊盘/导线/过孔位置整体偏 25.4 倍 → 飞出板外。
   这解释了"预览正常、导入失败"（预览用解析后的 mm，导入用二次换算值）。
   已引入 `mmOf()` 只给坐标用，`toMM()` 只留给光圈/宏参数；顺带修了钻孔槽孔漏除 `10^dec`。
3. **无 D 码的坐标行没沿用模态操作码**：Gerber 语义是无 D 码则沿用上一个 D01/D02/D03。
   旧实现一律当绘制 → P-CAD 的 `D2*` + `X…*` 会从 (0,0) 拉出一条假斜线，并把 (0,0) 写进
   包围盒（大偏移布局 `x∈[590,688]mm` 上直接撑到 689×726mm）。已加 `state.dCode` 模态码 +
   `state.hasPoint`（位置未定义时的裸 `D2*`/`D03*` 忽略，不写包围盒；首段裸 `D01` 当起笔）。
4. **光圈宏不支持 `$n` 参数化**：新增 `resolveApertureMacro()`（06-utils.js），
   支持基元 1 圆 / 4 多边形 / 5 正多边形 / 20 矢量线 / 21 中心矩形 / 22 中心圆角矩形，
   并做 `$n` 代入与 `+ - * /` 运算（Gerber 里 `X` 也是乘号）。求值用**手写递归下降**
   （不用 `new Function`，避免 iframe CSP 禁 eval）。解析器 `buildMacro()` 现在只拆块不求值。
5. **渲染器不换算光圈尺寸**：坐标换算过了但光圈没换算，英寸文件的线宽/焊盘小 25.4 倍
   （SD Mapper、上.pcbdoc 预览又细又淡）。已按 `file.data.units` 引入 `unitScale`
   （**钻孔层除外**——刀具直径解析时已换算成 mm）。

### 导入解析问题根因（7 文件实测，已写入 `Temp/导入解析问题根因分析.md`）

- **共同病灶 = `05-pad-tool.js` L335-338 的 `effMode` 推断只有 3 条规则**：
  `type3→'PAD'`（不看图层/不分 pad-via）、`type1|2→铜层 TRACK 否则 POLY`、`type4→保持 mode`（无标记时恒为 NONE）。
  → 7 个症状里 5 个源自这里。
- `rawCoppers` 是 `consolidate` 形参，`extractRawData` **从不产出** → 覆铜无专门通路。
- `tryMergeDrillToPad` 对单面焊盘直接 return 不合并 → pad 与 via 叠在同一坐标（"矩形焊盘变过孔"）。
- 走线变粗：区域轮廓 D01 复用当前光圈；1.4 铜层实测 `0.25mm`(9.84mil) 与 `0.85mm`(**33.46mil**) 同时存在。
- **段标记实测（重要，纠正一个假设）**：EasyEDA Pro **v2.1 与 v2.2 的段标记与铜层段落结构完全一致**
  （`G04 Copper Start* / G36 … G37* / Copper End*`，标记集 Copper/PolygonModel/Pad/Via/Track）。
  所以"v2.1 要单独解析器"在标记层面不成立，需另行确认差异。
- 来源格局：EasyEDA 标准版 **v6.5 无任何分段标记**；P-CAD/RS-274D 也无；KiCad/Sprint-Layout 无。

### 第五轮：导入解析修复（推断规则 + 图元通道），详见 `Temp/导入解析修复说明.md`

- **图元通道的核心 bug**：`importPrimitivesAPI` 把**嵌套**数组 `[[x,y,'L',...]]` 喂给
  `eda.pcb_MathPolygon.createPolygon()`，而官方签名只接受**平铺** `TPCB_PolygonSourceArray`
  → 返回 `undefined` → `pcb_PrimitiveFill.create(layer, undefined)` 抛错被吞 →
  **所有 FILL 静默创建失败**。这是"填充/覆铜/logo 丢失"的直接原因（预览走渲染器，导入走这条 API）。
  → 修：嵌套走 `createComplexPolygon`、平铺走 `createPolygon`，空值显式抛错。
- **孔类型**：官方 `EPCB_PrimitivePadHoleType` 只有 `ROUND`(长圆形)/`RECT`，**没有 `SLOT`**；
  槽孔 `["SLOT",maxS,minS]` → `["ROUND",minS,maxS]`。
- **图层 ID 与 API 枚举完全一致**（TOP=1/BOTTOM=2/MULTI=12/内层15-46/自定义71-100/HOLE=47/DRILL_DRAWING=56），
  焊盘建不出来**不是**层号问题。
- **`effMode` 重写**：区域 铜层→`POUR`(折线闭合轮廓) / 其它层→`FILL`；
  Flash 内层或「圆形+有钻孔+跨≥2铜层」→`VIA`，否则 `PAD`；绘制 铜层→`TRACK` / 其它→`POLY`。
- **⚠ 关键坑（坐标浮点差）**：同一物理点在不同文件间差 **0.004~0.014mm**
  （1.4 实测 flash `(8.000,-11.680)` ↔ drill `(8.001,-11.684)`）。用 1µm 精确字符串匹配只认出 9 个过孔；
  改成 **0.05mm 栅格就近归并**后认出 **99** 个。→ 凡跨文件配点一律用容差，禁止精确相等。
- 验证：`Temp/probe5.js`（严格 EDA mock，镜像官方多边形校验）走真实图元通道，
  7 个文件 **FILL/POLY 零创建失败**（修复前 FILL 100% 失败）。回归全绿，渲染哈希与基线逐位一致。
- 未决：铜层 G36 做「折线轮廓」还是「填充」只能二选一（用户备注要求折线，但 5_Gerber 曾把
  "填充变导线轮廓"列为问题）；圆形插件焊盘会被判成过孔（几何不可区分，需 X3 元件/网络信息）。

### 遗留

- **`core.autocrlf=true` 而仓库内文件是 LF**：孤儿克隆后文本文件会变 CRLF，`iframe/js/*` 的模板字面量
  会带上 `\r`。有需要时用 `.gitattributes`（如 `* text=auto eol=lf`）钉死，但会产生 renormalize diff，需先确认。
- `importPrimitivesAPI` 里 `create()` 未 `await`/未 `.catch()` → 失败是静默 unhandled rejection。
- `importPrimitivesAPI` 只支持 V2 数组格式（`handleExportToCanvas('api')` 强制 `pro_v2`，当前 OK）。
- 光圈宏基元 6(Moiré)/7(Thermal) 未绘制；含复杂表达式的宏仍是尽力而为。
