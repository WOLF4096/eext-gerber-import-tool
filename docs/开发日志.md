## V3.9.23

### 修复：EDA 内资源全部加载失败（相对路径在扩展里不成立）

现象：V3.9.21 把 21 个 js/css 改成相对路径后，GitHub Pages 演示恢复正常，但**在 EDA 里打开是白屏**。
根因：`sys_IFrame.openIFrame` 的第一个参数在类型定义里叫 `htmlFileName`，EDA 是按**文件名**从扩展包里取页面渲染的，
文档 URL 并不是 `/iframe/xxx.html`，所以 `js/x.js` 解析到了别的目录，21 个资源全 404。

走过但不可行的两条路（都已回退）：
- 同步 XHR 探测 + `document.write('<base href>')`（4e7b3f3）：EDA 里 XHR 不可靠，实测没修好。
- 无条件写两个 `<script>`（绝对 + 相对各一条）：站点根 = 项目根时两条都 200，脚本执行两次，
  `const` 重声明直接抛错 —— 本地调试环境必挂。

### 现在的做法：EDA 绝对路径优先 + 相对路径兜底

- `<head>` 最前面按 EDA 绝对路径加载一次 `iframe/js/00-env.js`；紧跟的内联脚本读 `window.__G2PCB_EDA_PROBE__`：
  **执行过 = 绝对路径可达 = 在 EDA 里**，没执行（404）= 演示模式。
  只认「执行过没有」，不依赖 onload / onerror 触发时机 —— 解析阻塞型脚本严格按文档顺序执行。
- 每处资源写两条：第 ① 条 EDA 绝对路径（`/iframe/js/…`、`/iframe/css/…`、`/images/…`、`/extension.json`），
  第 ② 条同文件相对路径（`js/…`、`css/…`、`../images/…`、`../extension.json`）。
  第 ② 条由 `g2pcbAlt()`（`document.write`，写在原位、顺序不串）、`g2pcbImg()`（onerror 换 src）、
  `fetch` 两条 try 兜底；**EDA 内第 ② 条根本不发请求**。
- CSS 同路：`<link href="/iframe/css/style.css">` 后跟 `g2pcbAlt('css/style.css')`。

### 回归与实测

- 线上 Pages 实测：用户站根 `/iframe/js/00-env.js` → 404；`/eext-gerber-import-tool/iframe/js/*.js` → 200；
  `/eext-gerber-import-tool/{images,extension.json}` → 200。即探测必然失败、兜底必然命中。
- 本地双形态复验（8458 站点根=项目根 / 8457 子路径严格 404 模拟 Pages）：ImportGerber 22 条 + About 4 条资源，
  两种形态下每条都至少一条 200，失败 0。
- `node Temp/sim-inline.js`（vm 按文档顺序跑内联脚本）：EDA 模式兜底请求 0 条；演示模式 21 条且顺序与文档一致。
- 编码约束遵守：HTML 无 BOM + CRLF，`.js` 保持 UTF-8 BOM + CRLF；改动脚本过 `node --check`。

### 已知代价

- 演示模式控制台会有 22 条 404（探测 1 + 20 js + 1 css），第 ② 条不能预扫描、21 个文件串行加载：
  复用连接实测 2.29s（单条均值 109ms，含本机代理延迟），并行约 1.7s。**EDA 内无此代价。**
- 已确认：演示模式慢一点可以接受，EDA 内必须快。

**`src/index.ts` 的 `eda.sys_IFrame.openIFrame('/iframe/ImportGerber.html')` 保持绝对路径** —— 由 EDA 宿主解析，

## V3.9.19

### 修复：覆铜填充与相邻铜（走线 / 覆铜轮廓）之间的发丝缝

现象：内层 2 导入后，覆铜填充的边缘与旁边的铜（走线、覆铜轮廓描边）之间有一条约 0.4 mil 的
发丝缝，高倍放大可见；同一份 Gerber 在别的工具里没有这条缝。

原因在「负片转正片」：**带挖空的覆铜必须拆成无孔简单多边形，拆分走 Clipper（只吃整数折线），
所以拆分前要把所有圆弧离散成弦**（弦高容差 `FILL_ARC_TOL = 0.01mm`）。弦是内接的 —— 弦永远
落在真圆弧内侧，于是整块填充的边界比 Gerber 里的铜小了一个弦高（最多 0.01mm ≈ 0.39 mil），
而且呈「弦中点最深、弦端点归零」的梳齿状。走线、描边铜、焊盘都保留真圆弧，只有拆过的覆铜变成
折线，圆边上的覆铜因此整体往里缩了一丝，与旁边的铜之间就裂出一条缝。
实测内层 2：填充总面积 1516.9mm²，而源区域是 1520.4mm² —— 差的 1.9mm² 全在圆弧上。

### 修复方式：拆分完成后把弦段还原成 ARC

`06-utils.js` 新增 `fillArcDefs / fillArcIndex / fillArcContaining / fillRingToOpsWithArcs`：
拆分前把外环与所有挖空环的圆弧参数（圆心/半径/起始角/扫角）记进一个包围盒索引；拆分后逐段判定
「这一段是不是某条源圆弧的弦」，把落在**同一条圆弧**上的连续弦段合并回一条 `ARC` 指令，
端点吸附回真圆。几何与 Gerber 完全一致，顶点数还比纯折线少 70%。

| 指标（`Gerber_PCB1_2025-01-11.zip` 内层 2） | 改前                | 改后                                                                                   |
| ------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------- |
| 填充路径指令数 / 其中 ARC                   | 4805 / 9            | **1419 / 805（−70%）**                                                                 |
| 填充面积（同一口径 0.02° 展平）             | 1516.93 mm²         | **1525.18 mm²**（源区域 1520.43）                                                      |
| 圆弧处的边界内缩                            | ≤0.01mm（0.39 mil） | **0**（与源圆弧逐条对齐，751 条中 747 条圆心误差 <0.01mm，余 4 条为 <3° 的近似直线段） |

### 顺带修掉的两个精度问题

1. `fillRingPoints()` 圆弧的**声明端点被漏掉**：`fillArcPoints` 只给中间采样点，末点要由调用方补 ——
   旧实现只在「退化弧」分支里补，正常弧靠「后面紧跟的 L 终点」蒙过去。只要后面紧跟的是另一条弧
   （源区域路径、以及圆弧还原后的填充路径都是这种形式），两段弧的交点就会被丢掉，弦直接跨过转角。
   实测层 15 因这一条少算 24mm²。
2. 标准版 `stdFlattenPath()` 固定 6° 采样：大半径圆弧的弦高会超差（r=10mm 时 0.0137mm），
   导出的 `SOLIDREGION` 同样比 Gerber 细一丝。现支持按**绝对弦高容差 0.002mm** 反算角步长
   （夹在 0.35°～6° 之间），本板实测只多 86 个点。

- 合缝面积对账：层 15 `delta = −0.18 mm²（−0.008%）`，层 16 `+4.6 mm²（+0.30%，与改前一致）`；
- 拆分块数：层 15 = 1 整片 + 3 个 <0.05mm² 碎岛（改前 1 + 1），层 16 = 23（改前 21）；
  碎岛是开缝本身切出来的真实小铜块，不是漏拆；
- `fill_ring_check`：`zeroSeg 0 / unclosed 55 / tooFewPts 107`（与改前逐项相同，没有新增非法环）；
- `fill_drop_check`：`fills 485 / fillPrims 491 / dropped 0`；
- `net_health`：207 个网络、`mixedClusters 0`、`sameNameMultiIsland 2`（与改前一致）；
- 专业版 V2 / V3 与标准版三种导出均无异常，画布渲染逐像素一致（画布读的是源区域，不受影响）。

## V3.9.18

### 修复：相邻填充之间约 0.2mil 的缝隙（铜皮不连通）

缝隙有两个独立来源，之前只修了其中一个：

1. **导出端（专业版）**：覆铜 `FILL` 的线宽字段还写着 **0.2**（V3 `"width": 0.2` / V2 数组第 5 位），
   EDA 按线宽把实心填充整体内缩 → 相邻两块之间再让出 0.2 mil。内层焊盘那处早就改成 0 了，
   只有覆铜这一处漏改。现已全部改成 **0**。
2. **导入端（两套导出都有）**：负片转正片时，带孔的覆铜要拆成「无孔简单多边形」，
   做法是从孔切一条 keyhole 缝到区域外 —— 缝宽 0.01 mm（0.39 mil），缝两侧就是两块填充，
   中间必然是空的。现把缝宽压到 **0.0002 mm（0.008 mil）**（`FILL_SLIT_HALF` 0.005 → 0.0001）。

### 优化：铺铜拆分策略（688 块 → 2 块）

旧策略是「每个孔各切一条缝通到区域边界」，227 个孔就在平面上割出 227 条切口，
一条内层平面被切成 **688 块**细碎填充。现在改成：

- 孔与孔之间按 **Prim 最小生成树**两两搭缝（O(n²)），整棵树只开 **一条**出口缝；
- 出口缝方向取「离区域边界最近的方向」（旧实现一律水平切到最右侧，长缝常把铜劈成两半）；
- 面积 < 0.001 mm² 的碎屑直接丢弃（`FILL_PIECE_MIN_AREA`）。

实测（`Gerber_PCB1_2025-01-11.zip` 内层 1，227 个挖空）：**688 → 2 块**（1 整片 + 1 个 0.03mm² 小岛），
相邻间隙 0.01 mm → **0.00022 mm**，专业版 FILL 条数 845 → 487（−42%），
铜面积对账 −0.002%（孔洞 340mm² 全部保留）。

> 记录一个走过的弯路：试过「拆完把每块向外膨胀 0.006mm」把缝合上 —— **不能用**。
> 膨胀会把缝合拢，而缝正是孔洞与外界的唯一通路，合拢后孔洞变成多边形内部的洞，
> 单环填充表达不了 → 被当成铜填死（实测 227 个孔 340mm² 全丢）。

验证与回归要点见 `docs/报告/铺铜填充缝隙与拆分优化_2026-10-18.md`；
脚本 `Temp/scripts/checks/fill_gap_probe2.js`、`fill_seam_check.js`、`fill_render_shot.js`、
`fill_drop_check.js`、`fill_ring_check.js`、`net_health.js`（后三个为既有回归，改前后结果一致）。

## V3.9.17

### 修复：顶层焊盘名称里混进底层焊盘名称

- 现象：按面拆成四层后，顶层焊盘名称里仍会看到几条明显属于底层的名称（反之亦然）。
- 根因：**只按飞针文件的 `LAYER` 过滤是不够的**。焊盘名称的匹配是「先中心 2.5mil、再框内最近」，
  而框内匹配会框到隔壁元件的引脚 —— 顶面焊盘的包围盒里套到一个记在 B 面的引脚，就把它画到顶层去了。
  实测本板 910 条标注的 `side` 与焊盘自身铜层不符，其中 **798 条是框内误配**，112 条是引脚正中
  但飞针面与铜层确实不一致。
- 修法（09-ui.js `ensureFlyingLabels`）：
    1. 先按焊盘**自己的铜层**限定可匹配的面（`pad.top` → 只找 T、`pad.bottom` → 只找 B）；
       只有内层铜、两面都没数据的盘才退回按飞针面判断；

## V3.9.11

### 性能：大板导入 3 倍提速（同一份 Gerber 与 V3.9.10 逐像素一致）

现象：`Gerber_PCB1_2025-10-16.zip`（21MB / 18 层 / 30.5 万条指令）导入渲染 43s，
V3.3.0 只要 3s。定位到四处随数据量放大的开销：

- **`mergeSegments` 是 O(n²)（最坏 O(n³)）**：pool 数组每接一段就全表重扫，
  折线越长越慢。本板 10 万条线段 → 一次导入 3.2s，占整体的 45%；
  而 V3.3.0 时代这段几何根本不参与渲染（见下条），所以显得"飞快"。
  改为「端点 0.05mm 栅格索引 + 前后两向生长」，整体 O(n)，耗时 3.2s → 0.29s。
  衔接优先级仍按旧实现（先 tail≈起点、后 tail≈终点），保证成链结果尽量对齐。
- **首帧为了画飞针标注要多做一遍全量几何提取**（V3.6.0 引入）：大板上这一遍
  正好把上面那个 O(n²) 跑满，这是 V3.3.0 → 3.6.0 突然变慢的直接原因。
- **`autoFitView` 的全量分位数**：把上百万个坐标点全部入数组再 sort 两次（0.95s）。
  改为「先数总量、按 stride 抽样到 ≤6 万点」——0.2%/99.8% 分位数对抽样不敏感，
  小板 stride=1 行为完全不变。0.95s → 0.07s。
- **主画布绘制**：每层都全屏 `clearRect` + 全屏 `drawImage`（16 层 × 数千万像素）；
  每颗焊盘都要重跑一次宏表达式求值、每颗都 `save/translate/restore`。
  改为「按图层内容包围盒只清/只拷那块矩形 + 光圈级缓存宏轮廓与参数数组」，
  3200×2000@2x 下单帧 1.36s → 1.15s，放大到局部时 473ms → 44ms（10 倍）。

附带的稳健性改动：

- 面板 resize 合并（120ms 防抖）：EDA 撑开面板会连发几十次 resize，
  大板每帧 1s+，不合并会被放大成几十秒。
- 修掉图层包围盒跳过时的 `bufCtx.save()` 未配对问题（会污染后续图层的变换）。

验证（`Temp/perf/` 下 bench/stage/cmp/redraw/stdcmp 五个脚本，Chrome 无头）：
本板导入 7171ms → 2325ms；4 个样本（2025-01-11 / 05-21 / 06-10 / 10-16）的
折线总长、圆弧数、焊盘数、填充数、画布像素指纹**全部逐项一致**。

## V3.9.8

### 修复：矩形 / 异形焊盘与导线判不连通，导致同一网络被拆成两个名字

- 现象：焊盘 A 飞针标注 `NET1`、焊盘 B 标注 `NET2`，两者之间有一条导线把它们连起来，结果仍是 `NET1` + `NET2` 并存（导线只归到其中一个），电气上明明连着却出现飞线
- 根因在**几何连通判定**而不是改名规则：`netConnected` 处理「线段 vs 多边形焊盘」时，三条判据都覆盖不到「**导线端点正好搭在焊盘边界上**」：
    1. 边相交用严格叉积，端点落在边上返回 false；
    2. 端点是否在多边形内（ray casting）对边界点不可靠；

- 新增判据：**线段到多边形「边」的最近距离 ≤ 线宽/2** 也算相接（`netSegSegDist2`，相交返回 0，否则取四个端点到对边的距离最小值）
- 验证 `Temp/net_conflict_probe.js` **13/13**：圆形/矩形/长圆的「穿心」「端点贴边」两种接法、两段导线接力、仅一个焊盘有网络名，全部合并为 `NET3`

## V3.9.7

### 新增：标准版相邻导线链式合并

- 同层 + 同线宽 + 同网络 + 端点相接（0.001 mm 量化）的 `TRACK` 合并成**一条多点 TRACK**：
  `TRACK~1~1~<net>~4062 3547 4081.5 3547 4090 3538.5 …~gge3656~0`
- 链在**端点（度 1）**与**分叉（度 > 2）**处断开，分叉拆成多条链各自输出 → **拓扑与几何都不变**；纯环输出首尾闭合点列
- 折线（POLY）拆成相邻段一起参与合并，所以「折线接导线」「折线接折线」也能串起来
- **圆弧（ARC）不参与合并**：标准版 ARC 是曲线图元，并进 TRACK 会变直
- 实测：`0802-2` 板 5410 段 → 679 条 TRACK（587 条多段，最长 167 点），总长误差 **0.0007 mm**；`pcb1` 339 段 → 145 条

### 变更：网络名冲突的第二种触发方式也改名 NET\*

- 除了「两个分量各带不同网络名却被合并」，现在**分量内本来混着多个网络名**也会改名 ——
  典型场景是两个不同网络的焊盘通过一段**无名导线**连到一起（`union` 阶段看不到网络，
  只有定名阶段才能发现）。此前这种情况只计 `mixedClusters` 然后按票数沿用其中一个名字
- 合成用例 25/25；4 个真实板（最大 24 368 图元）`renamedClusters=0`、`mixedClusters=0`、多岛 0

### 修复：高 DPI 屏上图形与标注文字 DPI 不一致

- 根因：导出 PDF 时临时重设 `canvas.width`，浏览器会把 context 变换重置成单位矩阵；
  恢复尺寸后只有 `drawCanvas()`，而 dpr 缩放依赖 `resizeCanvas()` 里那句 `scale(dpr)` →
  图形按设备像素绘制（缩小 dpr 倍、偏左上），标注文字层用的是绝对 `setTransform(dpr)` → 两者错位。
  因为只在「导出过 PDF 之后」出现，看起来像「不定时」
- 修复：`drawCanvas()` 每次都用**绝对** `setTransform(dpr,0,0,dpr,0,0)` 进入绘制，不依赖历史状态；
  PDF 导出恢复现场改为调用 `resizeCanvas()`
- 顺手修掉 `drawCanvas` 里 `save()` 不配对导致的每帧 state 泄漏
- 新增 `watchDprChanges()`：窗口拖到不同缩放比例的显示器时 dpr 会变但不一定触发 resize，单独监听并重算画布
- 验证：dpr=2 的图形物理尺寸 = dpr=1 的 **2.002× / 2.000×**（回退修复则为 1.000×，可直接判定）
