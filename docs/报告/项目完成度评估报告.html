5.3 结论与瓶颈

本地 JS 侧完全不是瓶颈。15 个样本中，最重的板（47,161 条指令 / 25,024 个图元）端到端也只有 229 ms； 全套「提取 + 聚合 + 生成」在最大样本上合计 54 ms。链表增长基本线性：指令数每增加 1 万，导入耗时增加约 60–80 ms。

已经做过的优化

  • 画布重绘：requestDraw() + requestAnimationFrame 节流，鼠标连续拖动只重绘一帧
  • 视锥裁剪：按 viewState 算出世界坐标可视矩形，完全在视口外的线段 / Flash / 区域直接跳过；余量取「本图层最大光圈 + 2 px」，保证裁掉的确实看不见
  • 极性批处理：只在极性真正变化时才 stroke()，同层连续线段攒成一条路径
  • 自动适配抗离群：优先按板框层，否则用 0.2%–99.8% 分位，避免单个离群坐标把整板缩成一点
  • 跨文件配点用容差栅格：0.05 mm 网格就近归并，替代 O(n²) 两两比较

仍然存在的风险点

  • 图元写入不可预测：importPrimitivesAPI 是同步循环、0 次让出。本地循环只花 9 ms，但 2.5 万次 EDA API 调用的实际耗时无法本地测量 —— 这是当前唯一可能让界面冻结的环节，建议分批 + await + 进度条。
  • 渲染每帧重建排序：loadedFiles.slice().sort() 与 getZ 闭包在每帧重算，板层多时有小量浪费（可用脏标记缓存）。
  • drawRulers() 300 行：标尺绘制与主循环同帧执行，大尺寸画布下可考虑离屏缓存。
  • 巨型函数：generatePrimitives 930 行，任何性能改造都要先承担阅读成本。

六、建议的推进顺序

批次动作理由
第 1 批图元写入分批 + await 让出主线程 + 失败可见化（catch 后累加错误数并提示）唯一可能让 EDA 卡死的环节；改动集中在 1 个函数，收益最大。
第 1 批把 exportForStandard() / exportForOther_Pro() 两个入口要么实现、要么从界面移除消除「点了没反应」的错觉，成本极低。
第 2 批实现 Gerber X2 模式：%TF.FileFunction 定层 + %TA.AperFunction 定型直接根治「图层靠文件名猜」「圆形焊盘与过孔分不清」两个老问题，且 X2 文件在存量里占比不低。
第 2 批实现 RS-274D：G70/G71、G90/G91、G54Dnn、外部/内置孔径表老格式一旦单位或增量坐标判断错，整板全错，属正确性问题。
第 3 批覆铜挖空：LPC 区域与覆铜做多边形布尔差集（或改用「填充挖孔」）补齐「走线变粗」修复后遗留的隔离带缺失问题。
第 3 批把 Temp/ 下的回归脚本整理为正式测试目录并纳入版本库已有 6 个可用脚本（字节等价 / 外壳回归 / 图元契约 / 渲染哈希 / 性能），是后续重构的安全网。
第 4 批拆巨型函数、清理 console、补 HTML 转义、决定 locales/ 去留慢工，不阻塞功能。
报告由源码实测生成：模块规模取自 wc -l 与文件字节数；性能数据取自 Temp/perf.js（15 个真实样本，Chrome headless 实跑）； 格式支持矩阵与未完成项取自 iframe/js/** 源码与 Temp/导入解析修复说明.md。
