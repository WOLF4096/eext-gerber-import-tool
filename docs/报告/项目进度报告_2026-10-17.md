## 二、本轮（V3.9.9）解决了什么

### 2.1 问题一：同一个网络出现三个名字

**现象**（用户截图）：焊盘 `2/NET_4` 与焊盘 `2/NET_2` 之间有一根导线相连，导入后导线已经是 `NET1`，
但两个焊盘仍写着 `NET_4` / `NET_2`。

**定位过程**：改名规则本身是生效的 —— `buildNetAssignments` 的 `netOf` 里，两个焊盘和导线三者都已经是 `NET1`。
问题出在**生成图元时焊盘的取名顺序**：

```
焊盘 = 飞针 NET_NAME 优先  →  没有才用连通分量算出的名字
```

焊盘本身带着飞针网络名，于是把改名结果覆盖回去了；导线没有飞针名，所以只有它拿到了 `NET1` ——
对比之下才显得「焊盘没改」，本质是**赋值优先级**而不是算法错误。

**修法**：

| 位置 | 改动 |
|---|---|
| `06-utils.js` `buildNetAssignments` | 额外返回 `renamed`（Set：因冲突而整块改名的图元）。两条触发路径（合并时冲突 / 定名时 `votes.size>1`）都标记 |
| `05-pad-tool.js` 焊盘生成 | 新增 `isNetRenamed(pad)`：命中 → `netName = netOf.get(pad)`；否则维持「飞针名优先」 |
| 焊盘编号 / 组合 | **未改动**，仍来自飞针引脚匹配（实测编号仍为 `1` / `2`） |
| 标准版导出 | 无需改（本来只取 `netOf`），两条通道结果自然一致 |

**为什么不做成「一律以几何结果为准」**：几何判定存在误连的可能（例如焊盘正好压在覆铜上），
若让几何结果全量覆盖飞针名，一次误判就会把焊盘改成覆铜的网络名。现在只在**确认冲突**时覆盖，
正常分量仍然是「飞针文件说了算」。

### 2.2 问题二：位号图层

| 通道 | 原行为 | 现行为 |
|---|---|---|
| 专业版（源码导入 / 图元导入） | 文档层 13（不分正反面） | **装配层**：顶层 `9`、底层 `10`（底层带 `mirror`） |
| 标准版导出（`TEXT` 图元） | 文档层 12 | 文档层 12（**不变**） |

`02-config.js` 用三个常量表达这条规则：`FLYING_REFDES_LAYER_STD=12` / `_TOP=9` / `_BOTTOM=10`，
替换原来的单一 `FLYING_REFDES_LAYER`。这样装配图 / 钢网图按面查看时能单独看到位号。

## 七、已知缺口与风险

**功能缺口**

1. 真彩图片（`.FCTS/.FCBS/.FCBO`）离线无解 —— RSA 封装的 AES 密钥在服务端，无任何可解路径。
2. 光圈宏基元 6（Moiré）/ 7（Thermal）未绘制。
3. `%SR` 步进重复、Gerber X2/X3 的 `%TF`/`%TO` 属性未处理。
4. 图元通道无法创建 FPC 补强（EDA API 限制，已改为跳过 + 提示）。
5. 标准版不导出埋盲孔 / 元件组合（格式本身不支持）。
6. PCB/FPC 手动开关只改 UI 标记（含补强层时自动切 FPC 才是有效路径）。

**风险提示**

- 网络名为几何推算结果，冲突处会主动改名 `NET*`，**必须人工复核**（已写进协议与两处 UI 提示）。
- 跨软件 Gerber 的图层命名差异可能导致归层不准。
- 大量图元走图元导入会卡顿，大板建议走源码导入或工程文件。

## 十、给用户的行动建议

1. 用出问题的那块板重新走一次「通过源码导入」或「导出专业版」，确认焊盘网络与导线网络现在是**同一个名字**（`NET1` / `NET2`）。
2. 检查位号：顶层元件应落在「顶层装配」、底层元件落在「底层装配」（底层为镜像文字）。
3. 若某块连通区被报成 `NET1` 这类名字，说明那里确实有**两个不同网络被连在一起**，需要回到原始设计核对 —— 这是刻意的「显式暴露」而不是静默猜一个。
