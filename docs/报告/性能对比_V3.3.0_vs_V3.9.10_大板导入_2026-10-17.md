# 大板导入性能对比：V3.3.0（3s） vs V3.9.10（43s）

样本：`Gerber_PCB1_2025-10-16.zip` — 21MB / 18 个 Gerber 文件 / 16 个可见图层 / **305,637 条指令**
（含 4 个内层、7339 焊盘、25884 过孔、22248 导线、13396 条折线、9039 条文字笔画、800KB 飞针 JSON）

测量方式：Chrome 无头 + Playwright，同一台机器、同一份采样配置，用 `Temp/perf/*.cjs` 脚本跑；
每个版本都是"从拖入文件到 loading 遮罩消失"的墙钟时间。绝对值和用户实机不同（实机更慢），
但**各阶段的相对占比与版本间的倍数关系**是可复现的。

---

## 一、结论先说

变慢不是渲染"变差了"，而是 **V3.4.0 → V3.6.0 之间，首帧渲染开始承担一份额外工作**：

> V3.6.0 新增「飞针标注层」（引脚编号 / 网络名 / 元件位号）。要画这些标注，就必须在
> `drawCanvas` 里跑一遍 `PadTool.extractRawData + consolidate` 拿到焊盘几何 —— 而 V3.3.0
> 时代的渲染是**直接从解析后的指令逐条画**，根本不做几何提取。

这一遍额外提取，正好把 `mergeSegments`（折线拼接）里那个 **O(n²)、最坏 O(n³)** 的算法跑满：
本板 10 万条线段 → 单独吃掉 **3.2s（占整个导入 45%）**。再加上后面的几处线性放大项，
就叠成了实机上的几十秒。

## 二、逐版本二分（同一份 zip，墙钟）

| 版本 | 导入耗时 | 该版本最大的热点 |
|---|---|---|
| V3.3.0（单文件 HTML） | **1,849 ms** | 解析 `handleStd` 387ms、`drawCanvas` 43ms、无几何提取 |
| V3.4.0（拆模块 + 视锥裁剪） | 2,725 ms | `quantile` 576ms（autoFitView 全量分位数） |
| **V3.6.0（新增飞针标注层）** | **7,689 ms** | `mergeSegments` 1,839ms + 提取循环 933ms + 675ms |
| V3.8.0 | 7,949 ms | `mergeSegments` 1,989ms |
| V3.9.0 | 8,302 ms | `mergeSegments` 2,934ms |
| V3.9.6 | 8,095 ms | `mergeSegments` 2,620ms |
| V3.9.10 | 8,936 ms | `mergeSegments` 3,222ms（45%） |
| **V3.9.11（本次）** | **2,325 ms** | 解析 0.5s / 几何提取 0.3s / 绘制 0.5s，已摊平 |

## 三、V3.9.10 的时间都花在哪（阶段计时）

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 解压 + 读 18 个文件 | ~250 ms | JSZip 解压 21MB + UTF-8 解码 |
| 解析全部 Gerber | ~500 ms | `handleStd` 353ms、正则 45ms、`parse` 108ms |
| 自动适配视图 `autoFitView` | ~950 ms | 上百万个坐标点全量 push + **两次 sort** 算 0.2%/99.8% 分位数 |
| **首帧 `drawCanvas`** | **5,242 ms** | 其中 3,200ms 是 `extractRawData`（几乎全是 `mergeSegments`）、420ms `consolidate`、约 700ms 真正的画布绘制 |
| 杂项（建表、属性、日志） | ~100 ms | — |

`mergeSegments` 内部长这样：每接上一段就 `pool.splice` 掉、然后**从头重扫整张表**，
外层还有 `while(changed)` 直到没有变化 —— 一条长轮廓（上万段）就是平方甚至立方级。

## 四、实机 43s 与无头 8.9s 的差从哪来

无头环境只跑出 8.9s，实机 43s。差值来自"随画布面积放大"的那部分工作，实测：

| 画布 | V3.9.10 单帧重绘 | 其中 `drawImage`（每层全屏拷贝） |
|---|---|---|
| 1400×900 @1x | 639 ms | 205 ms |
| 2400×1500 @1x | 854 ms | — |
| 3200×2000 @2x（5760×4000 = 23M 像素） | 1,385 ms | **675 ms（48%）** |

也就是说：
1. **每层都全屏 `clearRect` + 全屏 `drawImage`**，16 层 × 数千万像素；
2. 单帧成本随像素线性涨，4K/高 DPI 面板上单帧就 1s 以上；
3. EDA 打开面板 / 拖分栏会连续触发 resize，每次 resize 都 `requestDraw` → **重绘会叠成 N 帧**。

这三条叠加，是"同一份代码在无头里 9s、在 EDA 里 40s+"最合理的解释。

## 五、改了什么（V3.9.11）

| # | 位置 | 改动 | 效果 |
|---|---|---|---|
| 1 | `05-pad-tool.js` `mergeSegments` | 全表重扫 → **端点 0.05mm 栅格索引 + 前后两向生长**（O(n)），保留旧的衔接优先级 | 3.2s → **0.29s** |
| 2 | `09-ui.js` `autoFitView` | 全量分位数 → **stride 抽样 ≤6 万点**（小板 stride=1，行为不变） | 0.95s → **0.07s** |
| 3 | `05-pad-tool.js` | POLYGON 焊盘去重 `rawPads.some`、钻孔去重 `findIndex` → **栅格索引** | ~0.8s → ~0.05s |
| 4 | `09-ui.js` `drawCanvas` | 每层先算内容包围盒：**整层在视口外直接跳过**；合成时**只清/只拷那块矩形**；宏轮廓与光圈参数按 `cmd.ap` 缓存 | 单帧 1.39s→1.15s；**放大看局部时 473ms→44ms** |
| 5 | `10-init.js` | resize **120ms 防抖**（尺寸稳定后只重绘一次） | 面板动画不再叠帧 |

顺带修掉一个真 bug：图层包围盒的提前 `return` 原本会跳过 `bufCtx.restore()`，
污染 buffer 的 save 栈 → 后续图层变换叠加（大画布下画面错位，缩放到局部却看不出来）。

## 六、验证（不是"看着差不多"）

`Temp/perf/cmp.cjs` 对 4 个样本做逐项 A/B（旧包 `Temp/perf/before3910` 与新源码）：

| 样本 | 折线/点数/总长 | 弧段 | 焊盘 | 填充 | 画布像素指纹 | 导入耗时 |
|---|---|---|---|---|---|---|
| PCB1_2025-10-16（本板） | 13456 / 101013 / 144654mm | 51248 | 7339 | 1548 | 4090670715 = 旧 | 7171 → **2325 ms** |
| PCB1_2025-06-10 | 1450 / 16937 / 26511mm | 12950 | 3631 | 1307 | 全等 | 2037 → 1166 ms |
| PCB1_2025-05-21 | 4623 / 30084 / 82386mm | 9005 | 6407 | 1636 | 全等 | 6760 → 1836 ms |
| PCB1_2025-01-11 | 193 / 2151 / 2351mm | 1160 | 805 | 464 | 全等 | 415 → 375 ms |
| FPC_PCB2_2024-12-31 | 与旧一致 | 同 | 同 | 同 | 全等 | 128 → 127 ms |

三态像素指纹（适配视图 / 放大 4 倍 / 平移）也全部一致。

唯一残留差异：折线在**分叉点**的"成链分组"略有不同（polys/texts 各差 0.4%），
几何、总长、圆弧、像素完全一致；标准版导出的 TRACK 条数 +24 / 18622（0.13%），
原因是旧算法在 T 型交叉口的贪心接续顺序无法在不恢复 O(n²) 的前提下逐条复刻。

## 七、如果实机仍然偏慢

运行日志（面板底部 `▶ / ✓ 步骤名 XXXXms`）已经分了段，先看哪一段占大头：

- `✓ 解析图层` 大 → 纯文本解析，只跟 CPU 有关，两版都慢（不在本次范围内）。
- `✓ 渲染画布` 仍是大头 → 下一步做两件事：
  1. 给 backing store 加像素上限（例如 >1600 万像素时按 dpr 折半渲染，再让 CSS 放大）；
  2. 把飞针标注的构建**延后到首帧之后**（先出板子画面，标注在下一帧补上）。
- `✓ 读取 / 解压文件` 大 → 换 `DecompressionStream` 流式解压，JSZip 换成 fflate。
