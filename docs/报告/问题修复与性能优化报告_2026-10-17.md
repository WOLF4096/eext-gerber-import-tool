## 二、问题 1：文档层标注（Dimension 段）整段丢失

**复现**：导入 `JT-XHD 4G FPC.zip` → 画布上文档层只剩一个矩形框，所有尺寸线、箭头、文字笔画都不见了；
走「通过源码导入」后同样缺失（说明丢失发生在**解析阶段**，不是导出阶段）。

**根因**：EasyEDA 把标注写在 `G04 Dimension Start … End` 段里。`extractRawData` 的段标记分支
（`05-pad-tool.js` 约 530-553 行）只认识 Pad / Via / Track / PolygonModel / Rect / Circle /
Image / Text / Copper / Drill Drawing —— **没有 Dimension**。于是：

- `mode` 在 `Dimension Start` 处没有被切换，停在 `NONE`；
- 该段内的 D01 线段走不到「折线流程」（`effMode === "POLY" | "IMAGE" | "TEXT" | "DRILL_SYM"`），
  被整段丢弃；
- 只有前面的 `Rect Start…End`（POLY）保留下来 → 画布上「只剩一个矩形」。

**修改点**（`iframe/js/05-pad-tool.js`）：

```js
// 段标记分支新增
else if (cmd.text.includes("Dimension Start")) { flushPoly(); mode = "POLY"; }
else if (cmd.text.includes("Dimension End"))   { flushPoly(); mode = "NONE"; }
// hasSectionMarkers 白名单补 Dimension（只有 Dimension 段的文件也要走段标记分支）
```

**验证**（`Temp/scripts/checks/doc_dimension_check.js`）：

- 文档层折线：**0 → 196 条**（1604 个点，总长 1088.49 mm）；
- 导出图元 `POLY@13`：196 条（层号 13 = 文档层）；
- 画布截图可见 `4.000mm / 24.500mm / 2.000mm / 0.500mm / 10.000mm` 等标注文字与尺寸线。

## 三、问题 2：大量网络变成 `NET1`（负片平面被当成实心铜）

**复现**：导入 `Gerber_PCB1_2025-01-11.zip`（805 焊盘、10 624 连通图元），生成网络后：

```
最大连通块 9689 图元（占 91%），块内 106 个不同网络名 → 冲突 → 整块改名 NET1
stats: renamedMerges 105 / mixedClusters 1
```

也就是说「导线被连成一片」是**几何误连**，而不是命名规则的问题。

**根因（两层，缺一不可）**：

1. **清区包围盒退化成 0，隔离孔被整批丢弃**
   `05-pad-tool.js` 挂载 LPC（清除极性）清区时，用 `bboxOfPath` 算清区包围盒，
   并要求 `x1 > x0 && y1 > y0` 才算有效。而嘉立创内层平面的隔离孔绝大多数是**整圆 = 两段半圆**，
   两段圆弧的端点都落在同一条直径上 → **包围盒高度为 0** → 判为「无效包围盒」→ 该清区被丢弃。
   实测：收集 315 个清区，**250 个 bbox 无效被丢**，只挂上 65 个 → 平面基本保持实心 →
   落在平面范围内的所有焊盘/过孔都判成「与平面相连」→ 全板并成一个分量。

2. **多边形顶点提取不展平圆弧**
   `netPathToVertices` 只取圆弧的**终点**。覆铜轮廓把「焊盘周围的隔离缺口」画成圆弧，
   取终点等于用弦代替弧：弦向弧心内缩（矢高最大 0.29r），缺口变小 →
   焊盘被判成压在铜上。实测某过孔中心到覆铜边只剩 **0.199 mm**（真实隔离应 ≥0.5mm）。

**修改点**：

| 文件 | 修改 |
|---|---|
| `05-pad-tool.js` | `bboxOfPath` 先把圆弧按 `FILL_ARC_TOL`（0.01mm）展平再算包围盒；补充清区挂载统计日志（DEBUG） |
| `06-utils.js` | `netPathToVertices` 按 ≤22.5° 离散圆弧（半径 0.6mm 的缺口圆，弦高误差 <0.012mm） |

**验证**：

- 清区挂载：`节点 315 / 挖空 65 / bbox 无效 250` → **`挖空 318 / bbox 无效 0`**；
- 负片转正片：5 块覆铜 65 个挖空 → 8 块覆铜 **318 个挖空、拆成 961 块**无孔洞填充；
- 网络结果：`209 个分量 / 207 个沿用名 / 2 个冲突改名`；最大块 6606 图元**只含 GND 一个网络名**，
  `renamedMerges` 105 → **2**；两个剩余冲突已按设计改名为 `NET1`/`NET2` 供人工核对。

## 四、问题 3：「自定义/特殊」组勾选不同步标注层

**复现**：图层面板里勾选/取消「自定义/特殊」组 → 「引脚编号 / 网络名称 / 元件位号 / 补强名称」
四行的复选框不动，画布上的标注也不跟着显示/隐藏。

**根因**：`toggleGroup()` 只遍历 `loadedFiles`；而标注层是**虚拟行**（id 2001-2004），
状态存在 `flyingOverlayVisible` 里，DOM 上也没有 `.file-cb` 类 → 两处都匹配不到。
另外 `updateGroupCheckboxState()` 只统计文件行，单独取消一个标注行时组复选框不会变半选。

**修改点**（`iframe/js/09-ui.js`）：

- `toggleGroup`：同时翻转 `flyingOverlayVisible`（组内标注层），DOM 选择器改为
  `.layer-row[data-group=…] .col-vis input[type=checkbox]`（覆盖文件行与标注行），并显式设置组复选框 `checked`；
- `updateGroupCheckboxState`：组内总数 = 文件行 + 标注行，单行变化能正确落到「全选/半选/不选」；
- `toggleOverlay`：改单行后回调 `updateGroupCheckboxState`；
- 该组没有任何真实文件时，表头也生成可用的组复选框（否则整组无法开关）。

**验证**（`Temp/scripts/checks/group_toggle_check.js`）：

```
全关 → {"2001":false,...} DOM 全 false，组复选框 false
全开 → {"2001":true,...}  DOM 全 true，组复选框 true
单行取消（引脚编号）→ 组复选框 indeterminate=true, checked=false
```

## 五、性能优化（三块大板）

### 5.1 实测数据

| 板子 | 项目 | 优化前 | 优化后 |
|---|---|---|---|
| 1.6MB（3 631 焊盘 / 6 768 导线 / 1 307 填充） | 生成图元 + 网络 | **86.9 s** | **3.8 s** |
| 同上 | 物理网络 | **78.4 s** | **3.3 s** |
| 3.4MB（6 407 焊盘 / 30 514 导线） | 物理网络 | — | 6.5 s |
| 5.6MB（7 339 焊盘 / 22 248 导线 / 13 396 折线） | 物理网络 | 26.9 s（优化中途值） | **5.7 s** |
| 5.6MB | 生成图元 + 网络 | 28.2 s（同上） | **6.4 s** |
| 5.6MB | 整体导入（解压→解析→渲染） | 7.6 s | 7.8 s（提取/渲染为主，见下） |
| 任一板 | 缩放/平移单帧 | **373 ms（2.7 fps）** | **约 1 ms（快照路径）** |
| 任一板 | 完整重绘（停手后一次） | 373 ms | 333 ms |

### 5.2 为什么网络生成原来那么慢

以 1.6MB 板为例：连通候选对 88.3 万，`netConnected` 平均 8.2µs/次；5.6MB 板更极端：
**696 万候选对 + 32.3 万连通图元**（导出图元只有 5.9 万），其中 191 对「巨型多边形 × 巨型多边形」
单对就要 113 ms（两块 1 万～2 万顶点的覆铜做全量边求交 = 千万级运算），合计 21.6 s。

### 5.3 修改点（`iframe/js/06-utils.js`）

1. **边索引**：顶点数 ≥24 的多边形建 2mm 边网格 + y 分带索引（`netPolyEdgeIndex`）：
   - 边求交只取「查询矩形」覆盖到的边（通常个位数）；
   - 点在多边形内只用 y 分带内的边做射线法（O(V/分带数)）；
   - 两块多边形的求交矩形取**两者包围盒的交集**（相邻覆铜的交集常只是一条窄带）。
2. **巨型多边形用 Clipper 布尔求交**：两边都 ≥800 顶点时，直接算面积重叠（`ctIntersection`），
   单对 437 ms → 5 ms；结果按图元对象缓存（不能用 id 做键 —— 每次重建图元 id 会重复）。
3. **配对去重去掉全局字符串 Set**：改成「该对包围盒交集的最小角所在格子」判一次（不重不漏），
   省掉 8 百万条 `"id|id"` 字符串 + 数百 MB 内存。
4. **同源直连**：拆分出来的填充块（`src` 指回原始填充对象）与同一条折线的分段不做几何判定。
5. **连通判定用简化多边形**：Douglas-Peucker 0.05mm（只作用于连通图，不影响导出几何）。
6. **网格 5mm → 1mm**；`netLayersConnected` 加单层快速路径（避免数组 indexOf）。
7. **两块多边形时选顶点多的那个做「被索引多边形」**：否则会拿 4 顶点焊盘当主角、
   5000 顶点覆铜当配角，每对做 4×5000 次求交（实测 6 万对吃掉 5 秒）。

### 5.4 画布缩放/平移

**根因**：每帧都整幅重绘（19 层 × 全屏 clear + composite + 上万条 path stroke），
5.6MB 板 650ms/帧、1.6MB 板 333ms/帧 → 2~3 fps。

**修改点**：

- `03-state.js`：新增 `snapCanvas` 快照画布 + `snapInfo`（记录快照时的 offset/scale）；
- `09-ui.js`：`drawCanvas` 开头判断「正在交互 + 快照有效」→ `paintFromSnapshot()` 直接把上一帧位图按
  新变换贴回（一次 `drawImage`）；完整重绘结束时 `captureSnapshot()` 更新快照；
- 滚轮缩放、中键拖动都调用 `notifyViewInteraction()`：置交互态，150ms 无操作后自动补一次完整渲染；
- 导出 / PDF（`forceNoDpr = true`）**不走**快照路径，输出质量不受影响。

### 5.5 大数据量提示 + 运行日志

- **弹窗**（`ImportGerber.html` 新增 `#heavy-import-modal`）：`通过源码导入` 时若
  `loadedGerberBytes() > 500KB`，先弹【继续导入】【关闭】，文案给出实际大小与「建议改用导出专业版 V3」。
  关闭时不执行任何写入（`handleExportToCanvas` 直接 return）。
- **运行日志**（侧栏「导出选项」底部）：常驻面板（最多 200 行，时间戳），
  `appLog` 现在同时写「运行日志」和 DEBUG 文本框 —— 以前只有 DEBUG 打开时才可见。
- **步骤 + 预计耗时**：`stepBegin/stepStatus/stepEnd` 统一口径，导入侧覆盖
  「读取/解压 → 检测单位精度 → 解析图层 → 识别板层结构 → 渲染画布」，
  导出侧覆盖「准备源码头 → 提取数据 → 聚合 → 生成图元（含网络）→ 拼装源码 → 写入画布」；
  生成图元前用 `estimateExportMs()`（按 MB 估算，开网络 5s/MB、关网络 1.5s/MB）给出「预计约 Ns」。
  实测日志片段：

  ```
  19:36:12 ✓ 检测单位与精度 5ms
  19:36:12 ▶ 解析图层（共 20 个）
  19:36:12 ✓ 解析图层 202ms
  19:36:14 ✓ 渲染画布 1764ms
  ```

## 六、已知问题（本次未修，已定位并留证）

`Gerber_PCB1_2025-06-10.zip`（1.6MB）：内层平面在 Gerber 里是**一整块正向区域**
（15 289 顶点、**0 个 LPC 清区**），其隔离由轮廓上的凹口表达；当前连通判定把它当成实心铜，
导致 82 个网络并成 `NET1`（最大块 55 951 图元）。

- 该现象与本次改动**无关**：把 Clipper 求交路径关掉做 A/B，结果逐项一致；
- 方向：需要按「轮廓凹口」判定包含关系（例如对平面多边形做局部栅格化后判点），
  或直接以焊盘/导线是否与本层铜「有面积重叠」为准重算，工作量约等于再做一次本次的连通判定重构。
