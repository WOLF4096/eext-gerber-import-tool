## 一、你点名的三项

### 1. `isGerberText()`：扩展名 + 内容双过滤

- **原实现**：只排除了 `json/png/jpg/pdf/doc` 五种扩展名，其余一律放行。于是压缩包内的说明文件、P-CAD 的报告文件（`.ERR`）、**嵌套的压缩包**、纯二进制文件都会被当成 Gerber 解析。
- **现实现**：两道关卡
  1. 扩展名黑名单（压缩包 / 图片 / 文档 / 表格 / 报告 / 可执行 / 工程文件等）+ 文件名特征（`readme`、`必读`、`下单`、`说明`、`license`、`changelog`）；
  2. 内容特征探测：ZIP 魔数 `PK`、NUL 字节、不可打印字符占比 > 2% 直接判定为二进制；只有含 Gerber/钻孔特征标记（`%FS/%MO/%AD/%AM`、`G01~G04`、`M02/M30/M48`、`T<d>C<x>`、`X…Y…`、`D01/D02/D03`）才放行。
- **效果**：实测构造的陷阱包（内含 `nested.zip` + `readme_gerber.txt` + `report.ERR` + `PCB下单必读.txt` + 二进制 `broken.bin` + 一个正常 Gerber）——**6 个成员只放行 1 个**，且不再崩溃。
- **顺带**：散文件（非压缩包）分支以前完全不过滤，现在同样走这套判定。

### 2. 渲染 `type === 4` 前校验 `cmd.path`；`autoFitView()` 改用抗离群包围盒

- **`type === 4`（G37 区域）**：渲染与提取两端都加了 `Array.isArray(cmd.path)` 校验并跳过空路径。同时**在源头堵住**：解析器的 `record()` 现在只接受 `D01/D02/D03`，`D04~D09` 与 NaN 一律忽略——以前 `D4` 会生成一条 `type:4` 但没有 `path` 的指令，渲染时直接 `TypeError`，整个导入中断。
- **`autoFitView()`**：
  1. 有板框层（ID 11）时**以板框为准**；
  2. 其它图层若明显超出板框（>5%，典型是丝印文字伸出板外）时向外扩展，避免内容被裁掉；
  3. 没有可用板框时，用**坐标分位数（0.2%~99.8%）**&#x4EE3;替「所有图层的绝对坐标并集」，并保留退化回真实极值的兜底。
- **效果**：以前一个离群坐标就能把适配范围撑大数倍、整板缩成角落一个小点（正是"渲染看起来不对"），现在不会了。

### 3. 补 P-CAD/PADS 扩展名、`Gerber_CustomLayerN`、`G04` 单位/精度声明

- **P-CAD / PADS 扩展名**：`.TOP`（顶铜）、`.BOT`（底铜）、`.TMS`（顶阻焊）、`.BMS`（底阻焊）、`.TSL`（顶丝印）、`.BSL`（底丝印）、`.NCD`（钻孔）、`.BDR`（板框）、`.GML`（机械层）。
- **嘉立创自定义层**：`Gerber_CustomLayerN.GCL` → 自定义层 `70+N`（71~100）。
- **方位词后缀型命名**（旧规则只认前缀型，导致 `*_silkscreen_bottom.gbr` 被泛化的顶层规则吃掉、误判成**顶层**丝印）：补上 `silkscreen/silk/legend/mask/paste/solder mask/smdmask/assembly/fab/copper` + `_bottom / _top` 的两种语序；同时把 `smdmask`（嘉立创的锡膏层命名）排在 `mask` 规则之前，避免被误判成阻焊。
- **`G04` 声明解析**（新增 `detectGerberDeclarations()`）：
  - 精度：`%FSLAX36Y36`、`3 integers and 6 decimals`（兼容单数 `integer/decimal`）、P-CAD 的 `Numeric Format: 4.4 (XXXX.XXXX)`
  - 单位：`%MOIN/%MOMM`、`Dimensions in inches`、`Inch Units`、`millimeter/Metric`、`G70/G71`
  - 钻孔头：`;FILE_FORMAT=2:4`、`; Format: 2.4 (00.0000)`、`METRIC,LZ,000.00000`
- **优先级**：**文件自带声明优先于界面默认值**。旧实现里 UI 的精度默认值永远覆盖文件声明（且 `%FS` 只要文件写了就会被跳过），P-CAD 的 4.4、嘉立创标准版的 3.6 这类声明全部失效，坐标整体差 10 倍。现在只有用户**手动改过**精度/单位时才覆盖（`forceFormat` / `forceUnits`）。
- **处理器与内置规则取「更具体」的结果**：处理器给不出意见(57)时沿用内置文件名规则，避免 `<xxx>_silkscreen_bottom.gbr` 这类命名被回退成顶层。

## 二、顺带挖出并修掉的更深层根因

这几条才是"导入失败"的真正主因，没有它们，前三项修完仍然导不进去。

### ① 焊盘/导线全部依赖嘉立创专业版的私有段标记（核心）

`PadTool.extractRawData` 只用 `G04 Pad Start / Via Start / Track Start / PolygonModel Start / Copper Start` 这些 **嘉立创专业版私有标记**来判断「这一段是焊盘 / 过孔 / 导线 / 覆铜」。KiCad、Altium、P-CAD、**嘉立创标准版（EasyEDA v6）**&#x5BFC;出的 Gerber 都没有这些标记，`mode` 永远是 `NONE` → **焊盘、导线、折线全部不提取**，只剩钻孔能出过孔。

> 这就是"只有钻孔导入成功，其他全部失败"的直接原因。

**修法**：无标记时按「图层 + 指令类型」推断——铜层 Flash → 焊盘；铜层 Drawing → 导线；其它层 Drawing → 折线；区域 → 填充。有标记时行为完全不变。

### ② 单位双重换算：坐标已经是 mm，又被当成英寸乘了一次 25.4

解析阶段已经把 `X/Y/I/J` 换算成 mm，但 `extractRawData` 里对**坐标**仍然调用 `toMM()`（文件单位→mm）。文件是 mm 时看不出问题（嘉立创专业版都是 mm，所以一直没暴露）；**英寸文件**的焊盘/导线/过孔位置就整体偏大 25.4 倍，导进 EDA 后飞出板外。

> 这解释了"预览渲染正常，导入失败"——预览用的是解析后的 mm 坐标（对的），导入用的是二次换算后的坐标（错的）。

**修法**：坐标改用 `mmOf()`（只做有限性保护），`toMM()` 只留给「仍是文件单位」的光圈参数与宏参数。同一处还有一个「钻孔槽孔路径漏除格式小数位」的 bug（`manualToMM` 没除 `10^dec`），也一并修掉。

### ③ 无 D 码的坐标行没有沿用模态操作码

Gerber 里坐标行不带 `D` 码时，语义是**沿用上一个 D01/D02/D03**。旧实现一律当成「绘制」。P-CAD 的文件形如：

```
D2*            ← 裸 D2（无坐标）
D25*
X37709Y64289*  ← 无 D 码，应沿用 D2 = 移动
Y68279D1*
```

结果第一条坐标行被当成绘制，从初始的 (0,0) 拉出一条横穿板面的假直线（预览里的杂散斜线），并把 (0,0) 写进包围盒——板在 `x∈[590,688]mm` 这种大偏移布局上（P-CAD 的 SFG Cartridge / Carnivore2），一个 (0,0) 就把适配范围撑到 689×726mm，整板缩成 0.7% 覆盖率的小点。

**修法**：解析器维护模态操作码 `dCode`，无 D 码的坐标行按它记录；同时引入 `hasPoint`，位置未定义时的裸 `D2*`/`D03*` 直接忽略，不写包围盒。首段直接 `D01`（无前置 `D02`）时按惯例当起笔处理。

### ④ 光圈宏只支持 Primitive 4，且不会代入 `$n` 参数

现实里的宏几乎都是参数化的：宏体写 `$1/$2`，数值来自 `%ADDnn<宏名>,aXbXc*%`。旧实现只认「Primitive 4 且全是字面数字」的宏，于是

- P-CAD 的 `MTHOLE` / `ROUNDRECTNOHOLE` / `ROTOFFOVAL` …（含 `$2-$4` 这类算式）
- 嘉立创标准版的 `MACRO1..MACRO26`
- EasyEDA Pro 的 `RoundRect`、钻孔图的 `IconRect/IconTriangle/IconStar6`

要么不画，要么被后面的标准形状分支画成错误的矩形。

**修法**：新增 `resolveApertureMacro()`（06-utils.js）——支持基元 `1 圆 / 4 多边形轮廓 / 5 正多边形 / 20 矢量线 / 21 中心矩形 / 22 中心圆角矩形`，并做 `$n` 代入与 `+ - * /` 运算（Gerber 里 `X` 也是乘号）。求值用**手写递归下降**，不用 `new Function`，避免编辑器 iframe 的 CSP 禁掉 eval。渲染端与图元提取端共用这套求值结果。

### ⑤ 渲染器忘了换算光圈尺寸

坐标换算过了，但**光圈尺寸没有**：英寸文件里 0.01" 的线宽被当成 0.01mm 画，走线细 25.4 倍、焊盘小 25.4 倍。这就是 SD Mapper、上.pcbdoc 预览又细又淡的原因。

**修法**：渲染循环按 `file.data.units` 引入 `unitScale`（钻孔层除外——刀具直径解析时已经换算过），线宽、Flash 各形状、宏基元统一换算。

## 五、遗留事项

1. **`iframe/js/processors/` 目录还没被 git 跟踪**（7 个文件，`git status` 显示为 `?? iframe/js/processors/`）。`ImportGerber.html` 已经引用这些脚本，如果不 `git add` 就提交，别人克隆下来会是 404、整个页面打不开。**打包 `.eext` 不受影响**（构建走文件系统 + `.edaignore`）。
2. **`08-export.js` 的图元写入未 `await`**：`pcb_PrimitivePad/Via/Line/... .create()` 返回 Promise，现在既不 `await` 也不 `.catch()`，创建失败会变成静默的 unhandled rejection（这曾列入待办第 6 条：同步循环还会卡界面）。本次只加了「单行 JSON 解析失败不中断整批」的容错，并发/失败可见性没动——改动面较大，建议单独排期。
3. **`importPrimitivesAPI` 只支持 V2 图元数组**：代码路径里 `handleExportToCanvas('api')` 强制把 `clientVer` 设为 `pro_v2`，所以当前没问题；但如果以后要支持「V3 + 图元模式」，`JSON.parse` 需要改成解析 `meta||content`。
4. 剩余的光圈宏基元（6 Moiré、7 Thermal）未绘制；`$n` 参与顶点数、且含更复杂表达式的宏仍是尽力而为。
5. 版本号仍未统一（`extension.json` 3.4.0 / `package.json` 1.1.1 / CHANGELOG 缺条目），发版前记得处理。
