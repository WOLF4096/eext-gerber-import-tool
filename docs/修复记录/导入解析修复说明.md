# Gerber 导入解析修复说明（推断规则 + 图元通道）

> 本轮针对 7 个问题文件，**只改解析/导出这一侧**，未动解析器与渲染器。
> 全部结论均有实测数据支撑；验证走的是你实际使用的「通过图元导入」通道。

## 一、根因：两个层次的问题

### 1. 数据层：`effMode` 推断只有 3 条规则（`05-pad-tool.js`）

无段标记文件（KiCad / Sprint-Layout / P-CAD / **EasyEDA 标准版 v6.5**）里 `mode` 恒为 `NONE`，
于是 Flash 一律当焊盘、区域无差别当填充。这是 7 个症状里 5 个的来源。

### 2. 通道层：`importPrimitivesAPI` 的多边形格式用错了 API（`08-export.js`）

官方契约：

```ts
createPolygon(polygon: TPCB_PolygonSourceArray): IPCB_Polygon | undefined;
type TPCB_PolygonSourceArray = Array<'L'|'ARC'|'CARC'|'C'|'R'|'CIRCLE'|number>;   // 只接受「平铺」
```

而代码传的是 **嵌套** 的 `[[x,y,'L',...]]`（FILL 的 `path` 本身就是数组套数组），
`createPolygon` 直接返回 `undefined` → `pcb_PrimitiveFill.create(layer, undefined)` 抛错被 catch 吞掉
→ **所有填充静默创建失败**。这是"填充 / 覆铜 / 由填充组成的文字（logo）丢失"的**直接原因**，
也解释了为什么"预览正常、导入后什么都没有"——预览走渲染器，导入走这条 API。

同类问题：

| 位置 | 问题 | 官方契约 |
|---|---|---|
| FILL / POLY 多边形 | 嵌套数组喂给 `createPolygon` | 需 `createComplexPolygon` 或平铺 |
| 槽孔 holeShape | 用了 `"SLOT"` | `EPCB_PrimitivePadHoleType` 只有 `ROUND`(长圆形) / `RECT` |

另外核对确认：**图层 ID 与 API 枚举完全一致**（TOP=1 / BOTTOM=2 / MULTI=12 / 内层 15–46 / 自定义 71–100 /
HOLE=47 / DRILL_DRAWING=56），所以焊盘建不出来不是层号问题。

## 二、本轮改动

### `iframe/js/05-pad-tool.js`

1. **重写 `effMode` 推断**
   - 区域（G36/G37）：**铜层 → `POUR`（覆铜，折线闭合轮廓）**；其它层 → `FILL`（填充）
   - Flash：内层铜 / 圆形+有钻孔+跨层 → `VIA`；其余 → `PAD`
   - 绘制：铜层 → `TRACK`；其它层 → `POLY`（不变）
2. **新增「过孔 / 焊盘」区分预扫描**
   - 判定条件：**圆形光圈 + 同坐标存在钻孔 + 出现在 ≥2 个铜层** → 过孔
   - **矩形等非圆 Flash 永远不会被判成过孔**，直接消除"矩形焊盘变成过孔"
   - 关键坑：同一物理点在不同文件间有 **0.004~0.014mm** 的浮点差（`1.4` 实测 flash `(8.000,-11.680)`
     ↔ drill `(8.001,-11.684)`），最初用 1µm 精确字符串匹配 → 只认出 9 个过孔。
     改为 **0.05mm 栅格就近归并**后，1.4 认出 **99** 个过孔。
3. **覆铜改走折线承载**：`COPPER` / `POUR` 区域 → `rawPolys`（`createPolygon` 会自动闭合首尾）
4. **槽孔 holeShape**：`["SLOT", maxS, minS]` → `["ROUND", minS, maxS]`

### `iframe/js/08-export.js`（图元导入通道）

5. **FILL / POLY 多边形**：嵌套走 `createComplexPolygon`，平铺走 `createPolygon`；返回空则显式抛错
6. **孔类型归一化**：`SLOT` 与 `ROUND` 统一归一到 `ROUND`，并保证 `(短边, 长边)` 排序

## 三点五、追加修复：走线变粗（10mil → 33.5mil）

### 根因：`extractRawData` 完全忽略 `cmd.polarity`（LPC 清除极性）

`1.4_copper_top.gbr` 原文只有 3 次极性切换：`%LPD*%`(行 44) → `%LPC*%`(行 52) → `%LPD*%`(行 1180)。
文件把**同一批几何画了两遍**：

| 遍次 | 行号区间 | 光圈 | 宽度 | 极性 |
|---|---|---|---|---|
| 第一遍 | 647–932 | `G54D31*` | **0.85mm = 33.46mil** | **LPC（清除）** |
| 第二遍 | 1775–2060 | `G54D42*` | **0.25mm = 9.84mil** | LPD（实体） |

两遍的段数、总弧长、端点全部一致（0.25↔0.85 都是 62 段 / 96.3mm；0.50↔1.10 都是 83 段 / 155.4mm；
0.35↔0.95、0.30↔0.90、1.00↔1.60 同样成对）。这是 Gerber 表达「**走线 + 隔离带**」的常规写法：
先用 LPC 以较粗光圈挖出隔离区，再用 LPD 以真实线宽画铜。

**预览之所以没问题**：`09-ui.js` 的渲染器用 `cmd.polarity` 切 `destination-out`，天然正确。
**导出之所以错**：`extractRawData` 从头到尾没看 `polarity`，把 LPC 的隔离笔画也当实体导线生成
→ 板上凭空多出一批 0.85mm（33.46mil）粗线。

每条 LPC 也印证了配对关系：`1.4_copper_top` 暗(LPD)`t1:167 t2:234 t3:173 t4:10`
／清除(LPC)`t1:249 t2:250 t3:173 t4:25`。

### 改法

在 `extractRawData` 主循环里，G04 处理之后加一道：

```js
if (cmd.polarity === 'C') {
    if (cmd.type === 1 || cmd.type === 2 || cmd.type === 3) { currX = mmOf(cmd.x); currY = mmOf(cmd.y); }
    continue;   // 清除极性只用于挖空，不生成实体图元；但必须推进当前点
}
```

顺带把**覆铜轮廓的描边宽度**从「上一个走线的光圈」（最大 1.6mm）改为固定 **0.1mm** ——
轮廓是细线，不该用走线光圈画。

### 实测（1.4_copper_top）

| | 修复前 | 修复后 |
|---|---|---|
| 生成的 LINE 线宽 | `9.84 / 19.69 / **33.46** / **43.31** / **62.99** …` | `9.84(98) / 19.69(93) / 13.78(10) / 39.37(6) / 31.50(4) / 11.81(2)` |
| 样例图元 | `[..., 33.4646, 0]` | **`[..., 9.8425, 0]`** |

剔除数量与 LPC 数量逐一对应，未受影响的文件完全不变：

| 文件 | 导线 前→后 | 原因 |
|---|---|---|
| 1.4_Gerber | 514 → **216** | 去掉 298 条 LPC 清除笔画 |
| 0802-2 | 2239 → **903** | 去掉 1336 条 |
| 5 / 5_SD Mapper / 上.pcbdoc | 不变 | 无 LPC |
| 12层 / stm32 | 不变 | LPC 只在区域（t4） |

回归全绿：语法 17/17、结构等价性、外壳 15 项、空文档校验、处理模式框架；
渲染哈希 `1573435536` / `-2809515` 与基线**逐位一致**（渲染器本来就用极性，未受影响）。

### 代价

LPC 区域（覆铜里的隔离/反焊盘）现在被一并跳过 → **覆铜看起来会是实心的**，
少了隔离带与反焊盘。这是「无负片填充能力的 EDA 导入」的固有取舍：
要保留挖空语义，需要 EDA 侧支持「填充挖孔」，或由我们做多边形布尔差集（后续可做）。

## 四、未解决 / 待确认

1. **铜层 G36 的默认承载**：现按你的备注做成「折线闭合轮廓」。
   但你在 `5_Gerber` 那条里把"填充区域变成导线轮廓"列为**问题**——
   如果该板上那些区域其实是**填充块**而不是**覆铜**，就需要区分（目前只能在铜层上二选一）。
2. **圆形插件焊盘 vs 过孔**：Gerber 不含网络信息，两者在几何上无法完全区分。
   本轮按「圆形 + 有孔 + 跨 ≥2 铜层」判为过孔，因此**圆形插件焊盘也会变成过孔**。
   如果要更准，需要引入元件/网络信息（X3 的 `%TO.C/%TO.N`）。
3. **v2.1 与 v2.2**：实测两者**段标记与铜层段落结构完全一致**（`Copper / PolygonModel / Pad / Via / Track`），
   未发现需要单独解析器的证据。12 层这次的"填充/覆铜丢失"已由 FILL 格式修复解释。
4. 多边形的 **ARC 参数顺序**官方文档自相矛盾（正文写 `arcAngle endX endY`，示例读起来是 `endX endY arcAngle`）。
   现有代码沿用正文顺序，未改动；若发现有圆弧错位，这里是第一嫌疑点。
5. 尚未实现：EasyEDA 标准版 v6.5 的**专用**解析器（本轮靠通用推断已能出图元）、
   P-CAD 的 `MTHOLE / ROUNDRECTNOHOLE` 之外的宏、文字转图片。
